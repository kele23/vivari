Filesystem: opt-in `BootOptions.mirrorLane` persists VFS file bodies through an append-only journal in a dedicated worker instead of a per-file `createSyncAccessHandle → truncate → write → flush → close` on the FS worker's thread. The FS thread only appends to one journal handle; the lane fsyncs the journal once per drain and rebuilds the per-path OPFS files afterwards, so per-file fsync is traded for one journal fsync per drain (a tab crash is safe either way; an OS/power loss can drop the last drain's bodies, where the direct path fsynced each file) — measured in the downstream studio (Chrome 156): a 200 × 3 KiB project write drops from ~1.0 s to ~16 ms on the FS thread, and 1 000 edits from ~4.3 s to ~0.1 s. The lane serializes all journal/state mutations and its flush is single-flight, materializes the pending operations in order, and the manifest is only rewritten after a successful lane flush, so the index never names a body that exists only in the journal. A journal left by a crashed tab is replayed before the VFS restore, guarded against newer direct-path writes (a record is skipped when the index no longer lists its path or the OPFS body is newer), and a boot that does not use the lane discards it. A lane that cannot start — a second tab owns the `vv-vfs-journal` Web Lock, private mode, no worker support, or no answer within 5 s — is terminated and the tab mirrors directly; a lane failure after startup is contained the same way, with every path it had accepted since its last successful flush re-queued onto the direct path.
